# Visual LoRA: controlled rollout reuse experiments

The original `train_mapwise_grpo_visLoRA_trl.py` is not modified. A and B share
`_vislora_grpo_baseline_snapshot.py`, a frozen copy taken on 2026-09-11. The two
entry points change only module-local configuration/Trainer bindings in their own
process. Do not edit this snapshot when changing the old baseline script.

## Experiment definitions

| Run | Entry point | num_iterations | Treatment |
| --- | --- | --- | --- |
| control | train_mapwise_grpo_visLoRA_iterations_trl.py | 1 | Native GRPO |
| B | train_mapwise_grpo_visLoRA_iterations_trl.py | 2 | Reuse each complete newly generated batch twice |
| A | train_mapwise_grpo_visLoRA_replay_trl.py | 1 | Same-QA successful-history replay with shaped policy ratios |

All start from the original Qwen/Qwen3-VL-8B-Thinking model and fresh visual LoRA.
Init-adapter and resume are deliberately rejected for this first controlled run.
Saved checkpoints are evaluable; exact training resume with sampler/cache state
is not implemented. Use new output directories, never reuse old experiment paths.

## A: method and deliberate adaptations

Primary peer-reviewed reference: [ExGRPO: Learning to Reason from Experience,
ICLR 2026](https://proceedings.iclr.cc/paper_files/paper/2026/hash/15a296dc96baa12aaef4facdd391161f-Abstract-Conference.html).
The implementation borrows mixed old/new same-question groups (Eq. 4) and replay
policy shaping (section 4.2), **not the complete paper's experience-selection pipeline**.
See the [method text](https://arxiv.org/html/2510.02245v2#S4).

- Build the buffer online from this run only. Store at most two distinct,
  final-answer-correct, terminated trajectories per QA, with prompt hash, token
  IDs, pre-update token log-probabilities and generating optimizer step.
- Warm up for 11 updates; entries can be reused for up to 44 updates. These are
  preregistered engineering defaults, not claimed paper-optimal settings.
- Follow the SAME input QA order as the other arms. Select every other QA group
  for replay, alternating the selected half each dataset pass. A question having
  more successes never gives it more QA slots. Pick cached trajectories cyclically.
- For selected QA with available history, replace the fixed last completion slot
  by ONE old success, retaining three fresh responses (G=4). Select before seeing
  fresh rewards. Without history, retain four fresh responses.
- Generate all four fresh responses first to preserve the native VLM generation
  path; count the discarded response explicitly. This version does not claim
  reduced generation cost. It reuses TRL's decoding, masks, vision processing and
  reward computation after substitution, and recalculates the mixed-group advantages.
- Keep baseline binary correctness reward, group-standard-deviation scaling,
  dr_grpo length denominator, beta=0 and truncation masking. For fresh samples use
  the native clipped objective. For replay samples replace it by
  `-[w/(w+0.1)] * advantage`, where w is current / stored policy token probability.
  The replay shaping constant is NOT the KL beta. There is no SFT loss.
- No difficulty buckets, easy-QA retirement or current-entropy ranking: these
  would change additional variables and sampling exposure in the 44-QA experiment.
  Correct final answers do not establish correctness of every reasoning step.
- Probability convention matches TRL's temperature-scaled, pre-top-p forward
  probabilities. Together with success selection, group baselines and shaping,
  this is a biased practical surrogate; do not describe it as exact unbiased
  correction of the truncated decoding distribution.

The raw `train/rewards/correctness/mean` in A includes inserted successes and is
therefore biased upward by construction relative to B/control. Compare
`train/reuse/fresh_correctness` for retained fresh responses and, above all, the
identical greedy independent evaluations. Native clip metrics include replay
rows before shaping and are not a direct diagnostic of A's shaped objective.
All-correct mixed groups still have zero correctness advantages. A can supply a
positive contrast when fresh responses are wrong and a usable old success exists;
it cannot invent a successful solution for a question never answered correctly.

## B: on-policy, off-policy and learning rate

Policy means the model's conditional next-token distribution. On-policy samples
come from the current pre-update policy. After one update, old answers were
generated by a different parameter state: reusing them is off-policy.

For B, generate group D at theta0, update to theta1, then recompute log-probabilities
and gradients for D at theta1 while keeping the original behavior probabilities
and group advantages. TRL clips current/old ratios. This differs from doubling
the learning rate on a single gradient: the second gradient, clipping status,
Adam state and learning-rate schedule can all differ.

[Revisiting GRPO, ICLR 2026, Table 1 and Algorithm 1](https://proceedings.iclr.cc/paper_files/paper/2026/file/b4008025c2182bfe16fcc8566ee14d64-Paper-Conference.pdf)
distinguishes fixed-batch reuse (`i>1,v=1`) from the authors' primary approach
(`i=1,v>1`): keep an older generation policy for several iterations but generate
FRESH responses each time. B implements the former through TRL; it is not a full
reproduction of the paper's delayed serving-policy synchronization method.
Neither approach guarantees increasing greedy accuracy on these map questions.

## Fixed comparison and expected budgets

Use the SAME random or mixed JSON in every run, selected before inspecting A/B.
Default: 220 optimizer updates, lr5e-6, cosine schedule, warmup0.05 (11 updates),
BS2, GA8, G4, max1536, seed3407, original rank/alpha/image processing/thinking.
`--max-steps` overrides `--num-train-epochs`; never compare just epoch labels.

| Quantity, at 220 updates | control | A | B |
| --- | ---: | ---: | ---: |
| QA groups contributing per update | 4 | 4 | 4 |
| Completion training uses | 3520 | 3520 | 3520 |
| Fresh generated responses | 3520 | 3520, including discards | 1760 |
| Distinct generation passes over 44 QA | 20 | 20 | 10 |

Equal update budgets cannot ALSO hold fresh sampling budgets equal when reuse
changes. This difference is intrinsic to the treatment, and is explicitly logged.
Compare a secondary accuracy-vs-fresh-generated plot as well as accuracy-vs-update;
do not claim equal wall time or equal total exploration. Keep the existing matched
control when its config matches; `control` mode is available for a fresh control.

Every 20 updates save a checkpoint, keep 12 (11 saves through step220). After
training, evaluate each checkpoint and final adapter with do_sample=False on the
same 50 QA, report retained44, excluded6 and all50. Step0 is the RAW baseline,
not full-data checkpoint300. No early hyperparameter changes based on A/B curves.

## Files produced in each scratch run

- `run_config.json`, `reuse_manifest.json`: effective budget, arguments, versions,
  script/data/scorer hashes and deviations from paper.
- `reuse_metrics.jsonl`: generation/update-use counts, token counts, replay source
  age and per-QA mixed rewards. `qa_group_metrics.jsonl` logs the actual training groups.
- `checkpoint-*/success_replay_buffer.json` (A): token IDs, old log-probs and policy
  step for audit. This is not an automatic resume implementation.
- `checkpoint_eval/checkpoint_accuracy.csv`: compare `retained44_accuracy_percent`.

## Windows upload and Euler submission

Run on local **Windows PowerShell**, not inside SSH:

```powershell
& "C:\Users\junyhuang\Thesis\Euler_results\VisionLoRA\debug50\jobs\upload_debug44_reuse.ps1"
ssh junyhuang@euler.ethz.ch
```

The uploader copies the NEW Python files and data to the existing repo directories;
it places the new sbatch and evaluation helpers in scratch. It does not upload or
overwrite the original training entry point, and does not submit jobs.
The existing inference and exact-evaluation scripts must already be on Euler.

Run the following inside **Euler SSH Bash**. `mixed` is an example: if you choose
random, change BOTH commands to random.

```bash
sbatch --output="$SCRATCH/thesis/logs/%x-%j.out" --error="$SCRATCH/thesis/logs/%x-%j.err" "$SCRATCH/thesis/jobs/train_debug44_reuse.sbatch" A mixed
sbatch --output="$SCRATCH/thesis/logs/%x-%j.out" --error="$SCRATCH/thesis/logs/%x-%j.err" "$SCRATCH/thesis/jobs/train_debug44_reuse.sbatch" B mixed
```

These are independent jobs with distinct outputs and fresh W&B runs. They may run
concurrently when GPUs are available. Existing mixed/random jobs remain unchanged.
The job includes baseline inference, training, and checkpoint evaluation; no
additional dependent evaluation job is needed. All these phases share the 24h
allocation; if time expires after training, evaluate saved checkpoints separately.

TRL 1.12.0 is required; incompatible versions stop rather than silently run a
different algorithm. Local verification covers syntax, buffer/routing invariants.
CPU autograd loss checks run when torch is present, including automatically inside
the sbatch before model loading. Actual VLM backward, 4090 peak memory and the
remote pipeline still require a container smoke run; they were not executed on
the local Windows base environment.
